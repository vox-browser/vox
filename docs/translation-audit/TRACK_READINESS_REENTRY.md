# Preserve track source changes made by readiness observers

A translated track readiness observer can now select another resolved URL during a synchronous readiness notification without leaving the older processing invocation active. Previously, a callback during the loading notification could make the outer invocation fetch again after the replacement had completed. A callback during a loaded or failed notification could update the selected URL before the model was waiting for a replacement, and the outer invocation could still emit its old completion event.

The processing model checks its generation immediately after notifying observers of loading. For terminal readiness, it first clears the loading flag and arms the wait for a new URL, then notifies observers. A generation check after that notification suppresses an obsolete load or error event. The failure helper captures its own generation before notifying observers, so nested failure or recovery cannot make an old helper dispatch a second completion event. The existing fetch-result generation checks and completion-listener behavior remain in place.

This change concerns a changed resolved URL while the track remains hidden or showing. It does not change observer registration, iteration or mutation behavior. The translated observer loop still passes each callback the track's current readiness state, so later callbacks in an outer notification may observe state established by nested processing. It does not provide an immutable notification snapshot or an ordering guarantee for multiple observers. Same-effective-URL writes, source removal and mode changes to disabled during processing remain outside this fix.
