# Direct media controls teardown

Fix b50dabb686e394a39ee2a0780cbc08f2faf5a517 brings public MediaControls.destroy calls through the media owner's teardown barrier. An owned controller delegates to destroy_controls, keeping its slot occupied until destruction finishes and clearing it afterward. A standalone adapter temporarily holds the same barrier while it removes its listeners, timers, frame and owned shadow root, then restores the previous barrier state. create_controls rejects requests during that interval even when no optional controller is present. A preserving adapter never clears a different actual controller.

This closes the direct-entry gap left by e6cc092e. Previously a direct destroy of an owned controller could leave its destroyed record in the owner's slot; a callback could also recursively clear that slot and install an orphaned replacement before the outer shadow detachment completed. A standalone adapter likewise had no occupied slot to prevent reentrant creation. Both paths now finish with released activity roots and no accidental replacement; a later attribute change can create fresh functional controls.
