# Browser UI internationalization (i18n)

Browser chrome strings go through `browserui.tr()` so the UI can ship in
more than one language. English is the default and the fallback: unknown
locale codes and unknown keys resolve to the English string (or the key
itself), so English output is unchanged until a locale is selected.

## Locale selection

Resolution order in `browserui.ui_locale()`:

1. `VOX_LANG` (developer override, all platforms).
2. Explicit preferred list from settings (`set_preferred_languages`),
   first supported language wins; an explicit list with no supported
   language stays English.
3. OS locale: Unix `LC_ALL` > `LC_MESSAGES` > `LANG`, macOS
   AppleLanguages, Windows user locale.
4. `LANG` on macOS/Windows (Unix already consumed it in step 3).
5. English.

Values like `fa_IR.UTF-8` or `FA-ir` reduce to their base subtag (`fa`);
only locales in `supported_locales()` are accepted. The locale is resolved
once per process and cached (`refresh_locale()` re-resolves; tests call it
after changing the environment). The settings panel applies the stored
list at startup and on every successful save, which also refreshes the
cached locale so chrome re-renders in the new language.

Validation messages use the already-resolved chrome locale explicitly:
`browsersettings.localize_error(locale, message)` takes the locale as an
argument, so error text always matches the surrounding UI without the
settings module depending on the chrome module.

## Network identity

Applying a language list also pushes it to `loader.ResourceLoader`
(`Accept-Language` on outbound requests, `navigator.language(s)`), but
only when the user configured a list: the built-in `en-US` default is
otherwise untouched. See `apply_preferred_languages()` in
`browserapp/browser_settings.v` and `preferred_fetch_languages()` in
`requestserver/curl_request.v`.

## Lookup and formatting

- `tr(key)` / `tr_for(locale, key)`: plain lookup with English fallback.
- `trf(key, args)` / `trf_for(locale, key, args)`: substitute `{name}`
  placeholders from `args`. Patterns live in the tables (e.g. `find.status`
  is `{current} of {total}`), never in call-site string interpolation.
- `format_digits(locale, input)`: display-only digit shaping hook. The
  default is the identity; locales with non-Latin digits override it.
- Per-action overrides: helpers like `window_button_text()` first try a
  specific key (`window.close`) and fall back to the generic pattern
  (`window.button` = `{action} window`), so locales with their own word
  order only add keys.

## Call-site rules

- Never embed user-visible English literals in chrome code; use `tr()` /
  `trf()` / the helpers. Action ids, layout geometry, and test assertions
  on the English default stay as-is.
- Validation logic compares English messages; localize only at the display
  edge via `browsersettings.localize_error(ui_locale, message)`.
- The settings Languages field stores a comma-separated BCP47 list, most
  preferred first (`fa, en`); empty means the system language.
  `normalize_preferred_languages()` validates and canonicalizes it.

## Adding a locale `xx`

1. Add `browserui/browser_locale_xx.v` with the `xx_chrome_strings` table
   (exactly the `en` keys) and any digit/format overrides.
2. Register `xx` in `supported_locales()`, serve the table from
   `locale_table()`, and extend `format_digits()` when needed.
3. Add `browsersettings/settings_locale_xx.v` with `xx_error_messages`
   covering every `SETTINGS_ERRORS` entry in
   `tools/check_browser_locale.py`, and wire it into
   `supported_error_locales()` / `error_table()`.
4. Add `browser_locale_xx_test.v` / `settings_locale_xx_test.v` and extend
   the checker's `LOCALE_SPOT_CHECKS`.
5. Run `python3 tools/check_browser_locale.py` and the module tests.
